- v2.7.11：**朗讀破音字修正＋朗讀設定新增「讀完自動接下一章」**（使用者回報＋要求，附兩張朗讀創世記第1章的截圖）。
  - **破音字修正**：「分開」原本會被唸成「fèn」，「於是地發生」的「地」原本被唸成輕聲的「de」，都不是正確的讀音。比照既有的 `TTS_FIX` 破音字修正表（只朗讀，不影響畫面顯示的經文），新增兩筆全詞替換：`分開→芬開`（強制唸 fēn）、`地發生→第發生`（這個特定詞組裡的「地」強制唸 dì，是「大地」的地，不是語助詞的「地」；只換「地發生」這個完整詞組，不動其他地方「地」字的讀音，避免波及別處正確的讀法）。

- v2.7.10：**「讀取失敗：內容不是有效的 JSON」，重整頁面後才恢復正常**（使用者回報，附兩張截圖：第一張載入 bible.zh.nt.json 失敗，第二張重整後又正常，讀經進度沒有不見）。查出 `sw.js` 的經文快取有一個既有的漏洞：`fetch(req).then(res => { c.put(req, res.clone()); return res; })` 不管 `res.ok` 是不是成功都照存——部署剛完成那幾秒、或使用者網路不穩時，若剛好拿到一個 404／5xx 或內容不完整的回應，也會被當成「讀過一次」永久存進快取，之後每次都讀到同一份壞掉的檔案，要等下次 VERSION 再往上加才會被清掉，重整頁面通常救不回來（這次剛好自己好了，比較像是走運，不是真的修好）。修法：`sw.js` 的 cache-first／network-first 兩條路徑都改成只有 `res.ok` 才 `c.put()`；`app.js` 的 `fetchJSON()` 再加一層自救——`r.json()` 解析失敗時，新增的 `purgeCached()` 會把這個檔名從所有版本的快取裡清掉，換一個網址（帶時間戳記避開快取）重抓一次，還是失敗才真的把錯誤丟出來，使用者不用自己清瀏覽器快取或重裝 App。實測（Playwright 模擬第一次請求 `bible.zh.nt.json` 回傳截斷的壞 JSON，第二次才回傳正常內容）：畫面沒有跳出任何錯誤，馬太福音第1章正常渲染，確認自救有效、零錯誤。

- v2.7.7：**「從這裡開始朗讀」在已經正在朗讀時點下去沒有作用**（使用者回報，附截圖：畫面反而停在別的地方繼續唸）。抓到一個競速（race condition）的錯：點畫線面板的「從這裡開始朗讀」時，程式是先 `ttsStop()` 收掉目前這一輪、再 `ttsStart()` 開新的一輪去唸指定的那一句；但如果**舊的那一輪還有一段語音正在等網路回應**（例如正在抓下一段的語音檔），舊的那個「等待」並不會因為 `ttsStop()`／`ttsStart()` 就真的消失——它只看 `spk.on`／`spk.abort` 這兩個旗標，而新的一輪一開始就把這兩個旗標重設成「正常在播」的樣子，舊的那個等待回來時會誤以為自己還是正確的那一輪，把畫面反白與音檔位置**搶回去它原本要唸的舊地方**，看起來就像「從這裡開始朗讀」完全沒有作用。修法：新增一個朗讀的「輪號」（`ttsGen`），每次真正開新的一輪就加一；朗讀相關的每一步（抓語音、開始播放、裝置語音接力）都帶著自己那一輪的輪號，網路回應回來時先核對輪號還是不是目前這一輪，對不上就直接放手、什麼都不做。實測（Playwright 模擬「舊一輪的網路回應刻意拖很久、比新一輪晚回來」的情境）：舊一輪的回應回來之後，畫面與朗讀位置仍然穩穩停在新一輪（使用者點的那一句）沒有被搶走；一般情況下（沒有競速）點「從這裡開始朗讀」、開始／暫停／接續／停止，行為與 v2.7.6 完全一致，零錯誤。

## 一、這本 App 做了什麼

| 項目 | 一般和合本 App | 本 App |
|---|---|---|
| 節號 | 每節前標數字，無法關 | **預設全部去除**；想要時一鍵開啟，節號是金色上標小字，不打斷文氣 |
| 章號 | 每章大標 | 淡雅章題，可一鍵隱藏；整卷連讀時完全消失 |
| 排版 | 一節一行 | **整章連貫成文**；詩歌體依底本 `\q1`／`\q2` 兩級縮排分行，詩題置中，段落空行保留 |
| 標點 | 舊式 `、` `．` | **新標點**：`，` `。` `？` `；` |
| 用字 | 喫、纔、甚麼、罷、麼、那裡、約但 | **現代通用字**：吃、才、什麼、吧、嗎、哪裡、約旦 |
| 代名詞 | 一律「他」 | 分「他／她／它」 |
| 助詞 | 耶和華阿 | 耶和華**啊** |
| 人名地名 | 大馬色、西乃、該撒 | **現代通用譯名**：大馬士革、西奈、凱撒（見下表） |

### 英文版經文來源（v1.5.0 起）

**World English Bible（WEB）**，來自 eBible.org 的 `engwebp_usfm.zip`。公有領域、現代英文，是把 1901 年 ASV 用今天的英文重新修訂的版本，讀起來順而不失準確。

處理方式與中文版相同：丟掉書名頁、大標題、小標題與平行經文串珠，只留章、節、段落與詩歌結構；原始檔裡逐字的 Strong 編號（`\w word|strong="H1234"\w*`）全部拆掉只留單字；腳註轉成可關閉的 `[…]` 夾註。

**核對**：66 卷 ／ 1189 章 ／ **31,103 節** ／ 28,126 個段落區塊 ／ 4,021,448 字元（約 72.6 萬個單字），「LORD」出現 6,685 次。

> 英文與中文的節數不同（31,103 對 31,021）是正常的——兩個譯本的分節本來就有差異，各自照自己的底本呈現。

### 中文版經文來源（v1.1.0 起）

底本是**《新標點和合本》（Chinese Union Version with New Punctuation, 1989）的原始 USFM 排版檔**——也就是出版社正式的新標點、現代用字版本本身，不是由舊版推算、合併出來的文字。這意味著：

- 標點、分段、詩歌體縮排、詩題，全部照出版社的原始標記（`\p` `\q1` `\q2` `\d` `\b`）呈現，不是程式猜的；
- 現代用字（吃、才、什麼、吧、嗎、哪裡、警醒、啊）是底本自帶的，不是外加的替換；
- 人名地名已是現代通用譯名，與《聖經新譯本》一致或更新。

## 二、功能

- **今日** — 讀經進度環（/1189 章）、繼續閱讀、今日默想（66 篇經典章輪替）
- **經卷** — 九大分類摺疊目錄 → 章號九宮格（已讀／目前章以顏色區分）
- **閱讀器** — 沉浸式排版、上下章、☰ 回目錄、**淨**（切換閱讀方式）、**A⁺**（四級字級）、**🔊**（朗讀）
- **閱讀方式** — 分章／**整卷連讀**；**顯示章**、**顯示節**各自獨立（閱讀器右上的「淨」鍵會循環四種常用讀法：全顯示 → 只有章題 → 全隱藏 → 整卷連讀全隱藏）：
  | 讀法 | 顯示章 | 顯示節 | 看起來 |
  |---|---|---|---|
  | 分章 | ✓ | ✓ | 有章題、有節號，一章一章讀 |
  | 分章 | ✓ | — | 有章題，經文乾乾淨淨沒有數字 |
  | 分章 | — | — | 純粹的經文，什麼標記都沒有 |
  | 整卷連讀 | — | — | 整卷一氣呵成，一口氣讀完 |
  「顯示章」與「顯示節」在「我的」裡可以各自開關，不受上表限制（例如只要節號不要章題也行）。整卷連讀時從第幾章進來就捲到第幾章，讀過的章仍會逐章記進度。節號依《新標點和合本》標示，金色上標小字
- **書籤** — 按 🔖 進入書籤模式（工具列的鍵會變成金色，上方出現提示條），**點一下讀到的那一句就加書籤，再點一下移除**，經文上會出現小書籤記號；再按 🔖 結束。書籤模式中點句子不會畫線。「我的」列出全部書籤可跳回或刪除。「繼續閱讀」會回到上次停下的那一句，不只是那一章
- **句子畫線** — 點一下畫線，再點一下開底部面板：8 色、寫默想、問小智、做成美圖、刪除
- **美圖工作室** — 畫線面板或「我的畫線」按 🖼 進入。**卡片內文**可以自己寫，也可以按「請小智寫祝福」讓小智照這節經文寫一段關懷的話；**上下兩行署名**（團體名／署名）都能自訂。做圖：9 版型 × 6 邊框 × 4 尺寸（9:16／4:5／方形／橫式）× 5 級領受字級，可加相片（背景／拍立得貼紙）。做影片：錄一段話（只有聲音或自拍畫面）、或不開口只配音樂，合成一支影片。「我的作品」收著所有成品，可播放／分享／下載／刪除。分享走系統分享選單（LINE／IG／FB 都可以），不支援就自動下載。排版有中文避頭尾，標點不會掉到行首
- **搜尋** — 全本經文搜尋，命中字句高亮，點擊直接跳到該章
- **小智AI屬靈同伴** — 帶入「目前在讀哪一章」的情境，附 10 題 321 理念範例問題，回答可收藏／朗讀／刪除；連不上時自動重試兩次，仍失敗會顯示原因
- **我的** — 統計、**語言（繁體中文／简体中文／English）**、字級／主題（自動·日·夜·**羊皮紙**）／閱讀方式／顯示章／顯示節／註釋顯示／朗讀聲音、我的書籤、我的畫線、我的收藏
- **PWA** — 可加到主畫面，經文讀過一次即離線可用

  tts : 'https://azure-tts.spch321.workers.dev'        // {voice, rate, sil, silc, sile, text}

## 六、小智回 403 怎麼辦

`xiaozhi-proxy.spch321.workers.dev` 從外面用 GET 打會回 **405**（只收 POST），代表 Worker 活著、也不是在入口就擋人。但這個 App 用 POST 送出去會回 **403**，而送出去的內容（`{system, messages}`、端點、標頭）與《321領導力》**逐欄比對完全相同**——所以是 Worker 那一端刻意拒絕這個呼叫，不是 App 組錯。

用「我的 → 連線測試」跑一次，看第①②項的回應內文：

| 回應內文 | 意思 | 要改的地方 |
|---|---|---|
| 提到 origin／referer／not allowed | Worker 有來源白名單，沒有放行這個 App | Cloudflare Worker 程式裡把這個網址加進白名單 |
| 提到 key／token／unauthorized | 金鑰或額度的問題 | Worker 的環境變數 |
| 空白或一串 HTML | Cloudflare 本身擋掉（WAF／Bot 防護） | Cloudflare 主控台的安全性規則 |

**最快的分辨法**：打開《321領導力》問小智一句話。那邊也連不上 → 是 Worker／額度的問題，跟這個 App 無關；那邊正常 → Worker 認得舊 App、不認得這個新的，把它加進白名單就好。
